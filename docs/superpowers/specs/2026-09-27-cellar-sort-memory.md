# Cellar sort: newest added by default, remembered per person — design

- **Date:** 2026-09-27. Branch `cellar-sort` (worktree `blindtastingapp-friends`), base production master `a23cd16`.
- **Owner, verbatim:** "cellars should default sort by newest added, but its saved on each profile what has been sorted by last".
- **Owner's standing instruction:** design, build and deploy without a further stop ("just write the design and then implement", "you dont have to ask before pushing, get it all done").
- **Review round 1 (2026-09-27)** amended C2, C4, C5, C6 and §3 below to what shipped; each amendment says what changed and why.

## 1. What exists today (read from the code)

- The cellar list (`src/app/cellar/cellar-bottles.tsx`, `CellarBottles`) keeps its sort in React state: `useState<SortKey>("bottles")`. It resets to "Most bottles" on every visit, on every device.
- `SortKey` (`src/lib/cellar/types.ts`) is `"bottles" | "name" | "added" | "yours" | "community"`. `SORT_ORDER` / `SORT_LABELS` / `sortRows` live in `src/lib/cellar/cellar-rows.ts`. `"added"` already sorts newest first by `lot.createdAt`, with **no tie-break**.
- `CellarBottles` renders on the owner's `/cellar` (`src/app/cellar/page.tsx`) and read-only on someone else's `/u/[id]/cellar` (`src/app/u/[id]/cellar/page.tsx`, `readOnly`). The read-only toolbar leaves out "Your score" (`cellar-toolbar.tsx`: `sortOrder` filters `"yours"`, and `sortValue` shows `"bottles"` when the state is `"yours"`), but the rows are still sorted by the state (`sortRows(filtered, sort)`), so the select and the order can disagree.

## 2. Decisions

- **C1 Default = newest added.** When a person has never chosen a sort (or their saved value is unreadable), every cellar list opens sorted by `"added"`. Its label becomes **"Newest added"** (was "Added"; the owner's words). The other labels are unchanged.
- **C2 A deterministic "added" order.** `"added"` sorts by the date the row itself shows as "added {month}" — `addedDate(lot)` in `src/lib/cellar/format.ts`: the purchase date when there is one, else `created_at` — descending, then by `lot.createdAt` descending, then by `bottleTitle` ascending, then by `lot.id` ascending. Lots written in one transaction (a CSV import) share `created_at`, so without the tie-breaks their order is arbitrary and can shuffle between renders.
  - *Review round 1, the date.* The first cut sorted by `created_at` alone, but every row's "added {month}", the lot sheet's Added and the catalog page's "added {month}" all show `purchased_on ?? created_at` (`addedMonth`), so a bottle entered today with an older purchase date topped the default list reading "added Mar 2024" above rows reading "added Sep 2026". The app already defines "added" as that date in owner-approved copy, so the sort follows it rather than new copy (e.g. "bought {month}" for a purchase date). If the owner means "entered most recently" instead, the other fix is a copy change plus a one-line revert in `sortRows`.
  - *Review round 1, the titles.* Titles are compared with one fixed-locale collator (`Intl.Collator("en")`), never a bare `localeCompare`, in "added", "bottles" and "name" alike: a bare `localeCompare` takes the runtime's default locale, so the server render (Node's default) and hydration (the viewer's browser, e.g. da-DK, where "Aa" sorts after "Z") could order tied rows differently — a hydration mismatch, since the list is server-rendered.
- **C3 Saved per person, server-side, owner-only.** A new table:
  ```sql
  create table public.user_preferences (
    user_id     uuid primary key references public.profiles(id) on delete cascade,
    cellar_sort text check (cellar_sort in ('bottles','name','added','yours','community'))
  );
  ```
  - RLS on (not forced). Policies for `authenticated` only: SELECT, INSERT and UPDATE where `user_id = auth.uid()` (INSERT/UPDATE also `with check (user_id = auth.uid())`). No DELETE policy.
  - Grants: revoke all from PUBLIC, anon, authenticated; grant `select`, `insert (user_id, cellar_sort)`, `update (cellar_sort)` to `authenticated`. anon gets nothing.
  - Why not a `profiles` column: every member can read `profiles` ("profiles read" is `true`), a sort preference has no reason to be public, and the `profiles` client UPDATE grant is pinned exactly by the two migrations queued behind this one (sharing defaults, levels). A separate table touches neither.
  - The table is named for preferences in general, but this change adds only `cellar_sort` (YAGNI: no view, group or filter memory; the owner asked for the sort).
- **C4 Account deletion.** An AFTER UPDATE OF `deleted_at` trigger on `profiles`, `profiles_deleted_drop_preferences` (`WHEN (old.deleted_at is null and new.deleted_at is not null)`), deletes that person's row — the `profiles_deleted_drop_favourites` precedent. Its function is SECURITY DEFINER, `search_path = public`, EXECUTE revoked from PUBLIC, anon, authenticated and service_role. `scrub_deleted_account` is not recreated.
  - *Review round 1, the insert guard.* A BEFORE INSERT trigger on `user_preferences`, `user_preferences_guard` (function of the same name: SECURITY DEFINER, `search_path = public`, EXECUTE revoked from PUBLIC, anon, authenticated and service_role), reads the profile row `FOR SHARE` and raises 42501 "this account has been deleted" when `deleted_at` is set — the `profile_favourite_regions_guard` precedent (20260919141700). The drop trigger fires once, and the profile row is kept (so the foreign key is satisfied): without the guard an access token issued before the deletion (valid until it expires), or an insert racing the scrub, could write a row naming the scrubbed profile afterwards. `FOR SHARE` conflicts with the scrub's `FOR UPDATE`, so such an insert either commits first and is removed by the drop trigger, or waits and then sees `deleted_at`. It refuses every role, the owner included. The app's own path never gets here (`saveCellarSort`'s `getUser()` fails once the auth user is gone); the guard is the floor for a direct PostgREST call.
- **C5 Which sort a list opens with.** The server page reads the VIEWER's own row (`user_preferences`, `.maybeSingle()`, any error → no saved value) and passes it to `CellarBottles` as the initial sort. A pure resolver decides:
  - `resolveCellarSort(saved: unknown, readOnly: boolean): SortKey` — a valid `SortKey` is kept, anything else becomes `"added"`; in a read-only list `"yours"` becomes `"added"` (that option is not offered there).
  - The toolbar's select value and the rows' order both use the same effective sort (fixing today's "yours" mismatch in read-only lists: the select must never show one sort while the rows follow another).
  - The initial value comes from the server render, so there is no flash and no hydration mismatch (no localStorage, no URL parameter).
  - *Review round 1, the tab's own last pick.* `CellarBottles` opens on `openingCellarSort(savedSort, readOnly, viewerId)` (`src/lib/cellar/tab-sort.ts`): this tab's last Sort pick by the same viewer when there is one, else the server's value — both through `resolveCellarSort`. Why: the app does not enable Cache Components, so a page unmounts when you leave it, and browser Back/Forward remounts it from the router's cached payload however stale it is (Next's bfcache), while C6 deliberately never revalidates. Without this, `/cellar` → pick "Name" → a wine's `/catalog/{id}` → Back reopened the list on the payload's old sort even though the row held "name" (and the same for `/cellar` → `/cellar/collection` → Back, or someone else's cellar → their profile → Back; a Link fired while the save is in flight could also render the old row). The pick is module state, written only by the Sort change handler (and a no-op on the server, where module state is shared by every request); a full page load starts a fresh client module, so the server render and hydration both still use `savedSort`. It is keyed by the viewer's id (both pages pass `viewerId`), since signing out and in as someone else is a soft navigation and module state outlives it. Accepted residual: a pick made on another device after this tab's own last pick shows in this tab only after a reload.
- **C6 Saving.** Every change of the Sort select, on any cellar list (own or read-only), saves the viewer's choice: a `"use server"` action `saveCellarSort(sort: SortKey): Promise<{ ok: true } | { error: string }>` in a new file (exports only async functions; shared types in a plain module), which validates the key and writes the viewer's own row: `.update({ cellar_sort }).eq("user_id", uid).select("user_id")`; when no row came back, `.insert({ user_id, cellar_sort })`; on 23505 (another tab inserted it in between), the update once more (`writeCellarSort`, `src/lib/cellar/sort-preference.ts`). **Never `.upsert()`**: PostgREST's `ON CONFLICT DO UPDATE SET` names every payload column, `user_id` included, which C3 gives no client UPDATE grant, so every save would fail with 42501. (*Review round 1:* this decision first said "upserts the viewer's own row (`onConflict: "user_id"`)"; C3's grants and that wording could not both hold, and the code shipped update-then-insert, pinned by `sort-preference.test.ts` and the DB suite's "the PostgREST upsert shape is refused".) It does not revalidate or refresh — the list already shows the new order, and the tab remembers the pick for its own remounts (C5). A failed save keeps the on-screen choice and logs one `console.error` line (no error UI: a lost preference is not worth interrupting the person).
- **C7 Scope.** Only the sort. The list/grid view, grouping, filters, search and page stay as they are (per visit).

## 3. Tests

- **Vitest (pure, relative imports):** `resolveCellarSort` (every key, garbage, null, `"yours"` in read-only → `"added"`, `"yours"` on own → kept); `sortRows(…, "added")` tie-break (equal `createdAt` → title, then id) and newest first; `SORT_LABELS.added === "Newest added"`; `SORT_ORDER` unchanged in order and content. Review round 1: "added" follows `addedDate` (a purchase date wins; equal dates break on `created_at`, newest first) and the shown dates never increase down the list; "name", "added" and "bottles" order tied titles the same under a da and an en default locale; `openingCellarSort`/`rememberTabSort` (a fresh module opens on the saved value; after a pick a stale payload opens on the pick, on own and read-only lists; another viewer never inherits it; nothing is remembered on the server).
- **DB suite `scripts/user-preferences.test.mjs`** (the `scripts/tour-seen.test.mjs` / `training-room.test.mjs` harness: production, each test in a transaction that always rolls back, throwaway profiles, `USER_PREFERENCES_APPLY=<migration>` applies the file inside each test for the dry run):
  1. As a user: insert own row, update it, read it back; cannot read, insert or update another user's row (0 rows / RLS error); no DELETE.
  2. The check constraint refuses an unknown key.
  3. anon: no privilege at all; `authenticated` holds exactly SELECT, INSERT(user_id, cellar_sort), UPDATE(cellar_sort).
  4. Soft-deleting a profile (`deleted_at` set) removes its row; the trigger function's EXECUTE holders are the owner only.
  5. RLS enabled and not forced; exactly the three policies.
  6. (Review round 1.) The insert guard refuses a row for a deleted profile — a leftover token, the owner, and after `scrub_deleted_account` — with 42501 "this account has been deleted", and lets a live profile's insert through; it is the table's only non-internal trigger, BEFORE INSERT (tgtype 7), and its function's EXECUTE holders are the owner only.
- **Browser (main session, local production build, then prod smoke):** a demo account with no row opens `/cellar` on "Newest added"; change to "Name" → reload → still "Name"; a second tab/session shows "Name"; someone else's cellar opens on the viewer's saved sort; with "Your score" saved, someone else's cellar shows and sorts "Newest added"; phone 375 px toolbar unchanged. Review round 1: with no saved row, open `/cellar` ("Newest added"), pick "Name", click a bottle's title (`/catalog/{id}`), press Back — the list shows "Name", not "Newest added"; the same for `/cellar` → `/cellar/collection` → Back, and for someone else's cellar → their profile → Back; a bottle with an older purchase date sits by that date under "Newest added", and every "added {month}" line reads newest first.

## 4. Rollout

1. Migration `supabase/migrations/20260927110000_user_preferences.sql` — additive (a new table, policies, grants, one trigger on `profiles`, one BEFORE INSERT guard on the new table), with same-transaction pre/post asserts in the style of `20260925120000_training_room.sql`. Dry run with the pg applier, DB suite with `USER_PREFERENCES_APPLY`, apply, suite again.
2. App deploy (the deployed app never reads the table; the new app tolerates a missing row and a failed read).
3. Rollback: revert the app; the table stays harmlessly.
